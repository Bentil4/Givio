# Story 2.1: Create & Edit Events

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Admin,
I want to create a new Wedding or Funeral event and edit its details afterward,
so that I can set up each event's basic record before donation-taking begins.

## Acceptance Criteria

1. **Given** I am on the Create Event screen (`create-event-screen`), **when** I submit Event Name, Event Type (Wedding/Funeral), Date, and Host/Family Name (Venue/Description/Notes optional), **then** a new Event document is created with a unique system-generated ID, and `EventDataService`/`EventService`/the Dexie `events` table (created for the first time in this story) all reflect it (FR-EVT-001) — the event type is clearly labelled everywhere the event appears in the UI, and the document is created with `status: 'active'`, `assignedUserIds: []`, and `nextReceiptSeq: 0` (Epic 3/Story 3.6 relies on this field already existing — AD-8).
2. **Given** two events exist, **when** donations are later recorded against each (Epic 3), **then** they are linked via `eventId` and never shared across events — this story only lays the data-isolation foundation (the `eventId` field on `Donation` doesn't exist yet; nothing to implement here beyond ensuring every Event has its own unique, stable `$id`) (FR-EVT-002).
3. **Given** an existing event, not yet closed, **when** I edit any of its fields via `edit-event`, **then** the change is saved and a record is written to the `audit_logs` collection (entityType `event`, before/after values, my Admin ID, timestamp) — the Viewer UI for this log ships in Epic 4, but the write path starts here (FR-EVT-003). Event Type is **not** editable (prevents accidentally reclassifying a Wedding as a Funeral after donations may already reference it) — see Dev Notes. An edit attempted against a `status: 'closed'` event is rejected (the "not yet closed" qualifier is this story's own gate; the ability to actually *change* status to/from closed is Story 2.2's separate scope).

- [ ] Task 2: Data layer — `EventDataService` (AC: 1, 2, 3)
  - [ ] Add a `DATABASES` `InjectionToken<Databases>` to `src/app/data/appwrite/client.ts`, following the exact existing pattern for `ACCOUNT`/`FUNCTIONS`: `new InjectionToken<Databases>('DATABASES', { providedIn: 'root', factory: () => new Databases(client) })`.

  - [ ] Create `src/app/data/services/event-data.service.ts`, `EventDataService`, `providedIn: 'root'`, injecting `DATABASES` and using `appDb` directly (module import, like other Data-layer files will use `dexie`):
    - `async createEvent(input: { name: string; type: EventType; date: string; hostName: string; venue?: string; description?: string; notes?: string }): Promise<Event>`: builds the full `Event` object client-side (`id: ID.unique()` from `appwrite`'s `ID` helper — AD-4's client-generated-ID rule — `status: 'active'`, `assignedUserIds: []`, `nextReceiptSeq: 0`, `createdBy` from the caller's own session via `inject(AuthService).currentUser()!.$id`, `createdAt`/`updatedAt` as `new Date().toISOString()`), writes it to `appDb.events.put(event)`, appends an outbox entry (`op: 'create'`, `status: 'pending'`), then calls a private `trySyncNow(entry)` (see below). Returns the Dexie-persisted `Event` immediately regardless of sync outcome — the caller never waits on network.
    - `async updateEvent(id: string, patch: Partial<Pick<Event, 'name' | 'date' | 'hostName' | 'venue' | 'description' | 'notes'>>): Promise<Event>`: reads the current record from `appDb.events.get(id)` (throw `ServiceError('Event not found')` if missing), reject with `ServiceError('Cannot edit a closed event')` if `current.status === 'closed'`, merge the patch + bump `updatedAt`, write back to Dexie, append an `op: 'update'` outbox entry with `baseUpdatedAt: current.updatedAt` (AD-3's conflict-detection field — unused until Story 3.5's `SyncEngine` exists, but the shape must be correct now so nothing needs retrofitting later), call `trySyncNow`, then **write the audit log entry** (see Task 3) before returning.
    - `private async trySyncNow(entry: OutboxEntry): Promise<void>`: **this story's stand-in for the not-yet-built `SyncEngine`** (Story 3.5) — attempts the real Appwrite write immediately inline (not a background/reconnect-triggered drain): for `op: 'create'`, `databases.createDocument({ databaseId, collectionId: eventsCollectionId, documentId: entry.entityId, data: ..., permissions: [Permission.read(Role.label('admin')), Permission.update(Role.label('admin')), Permission.delete(Role.label('admin'))] })`; for `op: 'update'`, `databases.updateDocument(...)`. On success, mark the Dexie record's (implicit) sync state by deleting/marking the outbox entry `'synced'` (simplest: delete the entry — nothing reads `'synced'` entries until Story 3.5 adds a pending-count UI). On failure (offline or any `AppwriteException`), leave the entry `status: 'pending'` and swallow the error — **never throw out of `trySyncNow`**, since a network failure must not block the caller from having their locally-saved Event. Wrap Appwrite errors in `ServiceError` only where this service's own public methods can genuinely fail (Dexie write failures); a failed *sync* is not a failure of `createEvent`/`updateEvent` themselves.
    - **Permissions set directly at creation, not via Story 1.2's Function**: `assignedUserIds` starts empty and no existing Donations reference this brand-new event, so there's no bulk permission rewrite needing the Function's elevated trust (AD-2's stated reason for routing through it) — `Role.label('admin')` is sufficient here. Story 2.3 (Assign Operators) is where `assignedUserIds` actually changes post-creation and where the Function integration for events begins.

## Dev Notes

- **This project has zero Databases provisioned anywhere in Appwrite** (verified live via `appwrite-cli databases list` → `total 0`) and zero Dexie usage (verified via `grep` — confirmed by the Architecture Spine's own "Dexie ... currently zero usage — greenfield" note). This story is the first to touch either. Task 7's provisioning steps are not optional boilerplate — nothing in this story works live without them.
- **No `SyncEngine` exists yet** (that's Story 3.5, explicitly framed around Operator donation entries per its own epics.md wording and FR-OFF-004's literal text, which only formally requires *donation* entry/edit/receipt functions to work fully offline — FR-EVT-001 has no such requirement). But `create-event-screen.md`'s own design doc shows an offline indicator ("Event will be created locally and synced when online"), and AD-4 explicitly binds `EventDataService` to the same Dexie+Outbox rule as `DonationDataService`. **Resolved (user-confirmed) as**: `EventDataService` writes Dexie + an outbox entry (AD-4-compliant, so Story 3.5's eventual generic `SyncEngine` can pick up any leftover `pending` entries without EventDataService needing changes later), then attempts an immediate inline Appwrite push as a stand-in for the full engine. This gives real, working online functionality now (the common case for an Admin managing events) while staying structurally forward-compatible. **What this story deliberately does NOT build**: reconnect-detection, background retry, a pending-count badge, or a "Sync complete" toast — all explicitly Story 3.5's job.
- **Audit log write path**: `writeAuditLog` lives on `EventDataService` itself rather than a new `AuditDataService`, since epics.md's own Epic 2 implementation notes explicitly leave "the audit log write path mechanism" as an open question resolved by "the epic that builds `AuditDataService`" (Epic 4). Building a whole new Data-layer class for one `createDocument` call this story doesn't need would be premature — matches the project's established "don't introduce abstractions beyond what's needed" precedent (Story 1.3's "don't introduce a UserStore unless a second screen needs it"). **Known gap, flagged**: if `trySyncNow` leaves an update `pending` (offline), no audit entry is written at all yet, since one referencing a document not-yet-in-Appwrite would be meaningless — there's no mechanism to retroactively write it once a future sync succeeds. Flag for Story 3.5 or its own follow-up to close this gap once the real `SyncEngine` exists.
- **Permissions at creation are set directly by `EventDataService`, not via Story 1.2's Function.** AD-2's stated reason for routing permission changes through the Function is that bulk rewrites of *existing* Donation documents' permissions "need elevated trust" the calling Admin's own session may not have. A brand-new Event has no Donations yet and an empty `assignedUserIds`, so there's nothing to bulk-rewrite — `Role.label('admin')` is safely set directly, the same way any Admin-owned document creation would work. Story 2.3 (Assign Operators) is where `assignedUserIds` first changes post-creation, and where the Function integration for events actually begins.
- **Screen placement overrides the Architecture Spine's routing table.** The spine groups `create-event-screen`/`edit-event`/`event-detail` under the `feature/organizer/` row, but both this story's AC ("As an Admin...") and PRD §10.2's screen inventory ("Create / Edit Event | Admin only") are unambiguous that these are Admin-only. Placed under `feature/admin/` instead. **Flag for the user/PM** to correct the spine's table — this is a documentation drift, not an intentional design.
- **Design-doc drift, both flagged and excluded from scope** (same category Stories 1.1/1.3 already established a precedent for): `create-event-screen.md`'s "Allow organizers to..." framing and its "Allow donor verification"/"Show donation amounts publicly" privacy toggles (no such fields exist in PRD §9.1's `events` schema, not in this story's AC); `edit-event.md`'s "Event status selector: Active / Completed / Archived" (wrong enum values entirely — the real one is `active`/`paused`/`closed` per PRD §9.1 and Story 2.2's own AC) and its "Delete Event" button (no FR/AC anywhere authorizes hard-deleting an event in v1).
- **`nextReceiptSeq` isn't in the PRD §9.1 `events` table verbatim** — it's specified only in epics.md's enhanced Story 2.1 AC, sourced from AD-8's provisional-then-final receipt design (Epic 3/Story 3.6). epics.md is this project's authoritative "enhanced epics+stories" input (see this skill's own input-file table), so it takes precedence over the raw PRD table where the two diverge — same precedence Story 1.3 already established when reconciling epics.md against the raw PRD.
- **Money/receipt-number-generation/offline-donations ADs (AD-5, AD-8's *generation* half, AD-3's conflict-resolution UI) do not apply to this story** — `nextReceiptSeq` is only initialized here, never incremented (that's Story 3.6). Event-scoped permission derivation via `assignedUserIds` (AD-2) is only laid as a foundation (empty array) — Story 2.3 is where it actually does anything.
